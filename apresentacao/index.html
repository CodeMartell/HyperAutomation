Arquitetura de Software

Arquitetura Geral dos 5 Processos

Fluxo contínuo de dados transmitidos entre os setores da organização.

P1
Processo 1 — Atendimento: Leitura de solicitações, validação de documentação (Checklist) e classificação das pastas.
P2
Processo 2 — Organização: Extração de dados da Ficha (PDF/OCR), validação cadastral, atualização da Planilha Mestra Excel e arquivamento por Hash SHA-256.
P3
Processo 3 — Cadastro: Validação de entrada, checagem prévia de duplicidades (CPF) e integração com API Externa de Cadastro (retornando CLI-ID e fallback).
P4
Processo 4 — SAC: Emissão do protocolo SAC (SAC-YYYYMMDD-XXXX), notificação por e-mail/simulado, medição de latência ms e persistência em JSON.
P5
Processo 5 — Relatórios: Consolidação de métricas globais, cálculo da taxa % de sucesso e emissão de relatório gerencial versionado.
Reutilização de Código

Processos 1 e 2 Reutilizados

Manutenção das regras de negócio legadas das Releases 1.0 e 2.0.

Processo 1 — Setor de Atendimento

source/atendimento/main_atendimento.py
• Recebimento via IMAP ou leitura de diretório local fallback.
• Validação de 3 anexos obrigatórios (Identidade, Comprovante, Ficha).
• Movimentação automática para Documentos_OK/ ou Documentos_Pendentes/.

Processo 2 — Setor de Organização

source/organizacao/main_organizacao.py
• Varredura da pasta Encaminhados/.
• Extração via pypdf / OCR e validação de CPF, e-mail e maioridade (18+).
• Gravação em Planilha_Mestra.xlsx e arquivamento com Hash SHA-256 idempotente.
Setor de Cadastro

Processo 3 — Validação & Integração API

Validação de entrada, checagem prévia de duplicidade e resiliência via fallback.

1. Validação de Dados

Função validar_cliente() checa a presença dos campos obrigatórios (nome, email, cpf).

2. Duplicidade (CPF)

Função verificar_duplicidade() evita cadastros redundantes na base.

3. API & Fallback

integrar_api_cadastro() consome a API gerando CLI-ID. Se indisponível, aciona fallback_cadastro().

Serviço de Atendimento ao Cliente

Formatação de mensagens, protocolo auditável e notificação por e-mail.

Garantias do Processo 4


• Protocolo Único: Formato SAC-YYYYMMDD-XXXX gerado a cada atendimento.

• Registro JSON Auditável: Salvo em ERP_Portal_Fake/atendimentos/registro_atendimentos_sac.json.

• Monitoramento: Medição do tempo de execução em milissegundos (ms).

• Resiliência: fallback_sac() retém a carga sem interromper o pipeline.

Containerização

Dockerfile & Execução Containerizada

Ambiente reprodutível baseado na imagem oficial Python 3.14-slim.

# Dockerfile Otimizado
FROM python:3.14-slim
WORKDIR /app
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
RUN apt-get update && apt-get install -y --no-install-recommends build-essential curl && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
RUN playwright install --with-deps chromium
COPY . .
CMD ["python", "bot.py"]
Esteira de CI/CD

GitHub Actions (.github/workflows/ci-cd.yml)

Automação de testes e publicação condicional à aprovação da suíte.

1. Git Push / PR

Disparo automático em alterações na branch principal.

2. Job: Test (CI)

Instala dependências, valida sintaxe via compileall e executa pytest.

3. Job: Build & Push (CD)

Executa **apenas se os testes forem aprovados**, constrói a imagem Docker e envia para o GHCR.

Registry de Containers

Publicação no GitHub Container Registry (GHCR)

Distribuição segura da imagem de automação via GHCR.

Permissões & Autenticação

Autenticação automática no workflow usando token seguro nativo do GitHub:
permissions: contents: read, packages: write
password: ${{ secrets.GITHUB_TOKEN }}
